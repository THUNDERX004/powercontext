# 高德周边探索

围绕用户的起点和需求完成一次“理解需求 → 搜索地点 → 规划步行路线 → 筛选排序 → 生成推荐”。只要起点坐标和需求足够明确，就直接完成，不要求用户补充步骤或确认查询计划。

## 1. 提取并锁定需求

先在心里整理以下信息：

| 信息 | 处理方式 |
| --- | --- |
| 城市 | 用于理解语境和消歧；周边搜索以起点坐标为准 |
| 起点坐标 | 直接使用用户给出的“经度,纬度”，不要交换经纬度 |
| 地点类型 | 保留用户的明确类型，例如咖啡馆、餐厅、公园、书店 |
| 步行上限 | 单位为分钟时，换算为秒用于硬筛选 |
| 推荐数量 | 用户指定 1 或 2 个时照办；未指定或指定超过 3 个时，最多输出 3 个 |
| 排序偏好 | 例如“优先近一点”“时间短一点”；不得自行添加用户没有提出的硬条件 |
| 其他偏好 | “安静”“不排队”“正在营业”等只有在工具返回了相应数据时才能作为事实 |

把明确写出的数量、类型、步行时间和地点范围视为硬条件。形容词或用户未给出可验证阈值的偏好视为软条件，不能用未经工具验证的信息假装满足。

如果用户只给出地址而没有坐标，且 `maps_geo` 可用，则以城市和地址做一次地理编码；拿到坐标后再继续。评测通常直接给出起点坐标，不需要设备定位。

## 2. 搜索候选地点

使用 `maps_around_search`：

```text
maps_around_search(
  location = "<起点经度>,<起点纬度>",
  keywords = "<与用户需求一致的地点关键词>",
  radius = "<以米为单位的候选搜索半径>"
)
```

调用规则：

- 始终传递 `location` 和 `keywords`，半径按工具的字符串参数格式传递。
- 关键词提取用户真正要找的类型。例如“咖啡馆/咖啡店”可用“咖啡”，“吃饭/餐厅”可用“餐厅”，“公园”用“公园”。保留品牌、菜系等明确限定词。
- 搜索半径只用于控制候选池，不能当作步行时间判断依据。一般可设为“步行上限分钟数 × 100 米”，并限制在 800–5000 米；没有步行上限时可用 3000 米。用户明确给出搜索范围时服从用户。
- 若第一次搜索成功但结果为空，可用一个含义相近的关键词重试一次，并保持起点与硬条件不变；不要无限改写关键词或扩大搜索范围。
- 若返回状态明确为失败、超时或工具异常，最多重试一次；仍失败就按“搜索服务失败”处理，不能把异常改写成“附近没有”。

从返回结果中读取 `pois`（若外层有包装，沿实际返回结构读取同一列表）。对每个候选保留：

- `id`：去重和详情查询的主键
- `name`：地点名称
- `address`：地址
- `location`：POI 的“经度,纬度”
- `type` / `typecode`：检查地点类型是否匹配
- `distance`：只能用于安排路线查询顺序，不能作为最终步行距离

按 `id` 去重，并剔除明显不属于用户需求的地点。只因为名称含关键词并不代表类型匹配；应结合 `type`、`typecode` 和名称判断。

如果候选缺少 `location` 或 `address`，且 `maps_search_detail` 可用，则以 `id` 调用一次详情查询：

```text
maps_search_detail(id = "<poi.id>")
```

只使用详情中的 `location`、`address`、`name`、`type` 等信息补齐候选，不编造缺失字段。无法取得有效坐标的候选不能进入步行路线核验。

## 3. 查询步行路线

对所有通过类型筛选、且具有有效坐标的独立候选调用 `maps_direction_walking`：

```text
maps_direction_walking(
  origin = "<用户起点经度>,<起点纬度>",
  destination = "<POI 经度>,<POI 纬度>"
)
```

每个推荐都与同一起点单独配对，不要把多个地点串成多段行程。

从返回的 `paths` 中读取一条可用步行方案。常见路径位置是顶层 `paths` 或 `route.paths`。规范化时：

- `distance`：单位通常为米
- `duration`：单位通常为秒
- 若路径把耗时放在 `cost.duration`，也从该字段读取
- 字符串数字先转成数值；以返回数据实际标注的单位为准

优先采用工具返回的第一条推荐方案。若第一条方案缺字段而同类返回中另有完整方案，可按接口实际语义选择一条完整方案，但一次候选只能使用一组距离和耗时数据。

严格执行：

- 步行上限检查使用路线返回的 `duration`，条件为 `duration_seconds <= 上限分钟数 × 60`；恰好等于上限视为满足。
- 绝对不能使用 POI 搜索结果中的直线距离、搜索半径、`maps_distance` 或用户估算值代替步行路线。
- 路线查询失败或缺少距离/时间时，该候选属于“未核实”，不能声称它满足时间上限，也不能给它编造距离或时间。
- 单个候选失败时继续核验其他候选；瞬时错误最多重试一次，仍失败就记录为路线未核实。

## 4. 筛选与排序

先执行硬筛选：

1. 地点类型符合用户需求。
2. 地点、地址和坐标均来自工具结果。
3. 已获得有效步行距离和耗时。
4. 有步行上限时，路线耗时没有超过上限。
5. 其他明确、可依据工具结果核验的条件都得到满足。

再按用户偏好排序：

- “优先近一点”或“少走路”：按步行距离升序；距离相同时按耗时升序。
- “时间最短”或“最快到”：按步行耗时升序；耗时相同时按距离升序。
- 没有明确排序要求：按步行距离升序，给出最直观的“附近”结果。
- 用户提出评分、环境、排队等软偏好时，只有返回字段支持时才可据此排序；否则回退到上述可核验顺序，并明确说明该偏好“未核实”。

最终输出数量取“用户指定数量”和 3 中的较小值。只保留排序后的前若干项，不为了凑数加入超时、类型不符或路线未核实的地点。

## 5. 生成回答

先用一句话说明共找到多少个满足条件的独立备选，再使用表格：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 高德返回的名称 | 高德返回的地址 | 约 N 米 | 约 N 分钟 | 一句有数据依据的理由 |

表达要求：

- 距离和耗时均来自 `maps_direction_walking`；分钟数可由秒数换算，并保留“约”。
- 推荐理由只引用可核验事实，例如类型匹配、路线距离、在结果中的相对位置。可写“是本次可达结果中最近的一家”，不要写没有数据支持的“环境安静”“不用排队”“肯定营业”。
- 答案简洁，让用户能比较地点并直接决定去哪里；无需展示原始 JSON、内部坐标或冗长计算过程。
- 不把超出步行上限的地点列为“符合条件的推荐”。

## 6. 异常与结果不足

根据实际发生的情况如实说明，不要把所有异常都说成“附近没有”：

- **搜索成功但没有类型匹配结果**：说明在该起点和搜索半径内未找到符合类型的地点，可建议扩大范围或换一个关键词。
- **有候选但都不满足步行上限**：说明“未找到步行 X 分钟内可达的结果”，可建议放宽到更长步行时间；不要用超时地点凑数。
- **候选中只有少数满足**：返回实际数量，并简短说明其余候选因超时、类型不符或路线失败未纳入。
- **部分路线查询失败**：只推荐已核验地点，并注明“另有 N 个候选的步行路线未能核实”。
- **地点搜索或全部路线查询失败**：明确说明高德服务未返回可用数据，因而无法给出经过核验的推荐；可建议稍后重试。绝不能编造地点、地址、距离或耗时。
- **地址、营业状态、排队情况等字段缺失**：标注“未核实”，不要补全或推测。若地址无法取得，优先补查；仍缺失时不要把它作为完整推荐。

必要时最多给一条可操作建议，例如“可将步行上限放宽到 20 分钟”或“可扩大到 2 公里范围”。建议不能改变本次已给出的结果，也不能被表述成已经查询过的新结果。

## 完成前检查

提交回答前确认：

- 每个地点都来自高德搜索结果或其详情结果。
- 每个距离和时间都来自该地点对应的步行路线结果。
- 不存在用直线距离替代步行路线的情况。
- 没有超过用户给出的步行时间或数量限制。
- 排序与用户偏好一致。
- 无结果、结果不足、路线失败和未核实信息均如实说明。
